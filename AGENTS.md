# AGENTS.md — правила работы coding agent

## 1. Назначение проекта

Локальное кроссплатформенное desktop-приложение для одного пользователя, предназначенное для:

1. импорта индивидуальных планов преподавателей из XLSX, экспортированных из `nagr.stgau.ru`;
2. нормализации учебной нагрузки;
3. расчета ориентировочного объема почасовой оплаты;
4. ручного выбора дисциплин/групп/видов занятий, которые попадут в почасовку;
5. распределения выбранных часов по месяцам с сентября по май;
6. генерации двухчасовых занятий по допустимым датам и временным слотам;
7. заполнения шапки и таблицы заявления на почасовую оплату в DOCX.

Программа является инструментом **планового распределения**, а не системой учета фактически проведенных занятий.

## 2. Зафиксированный стек

- Python 3.12+
- PySide6 / Qt 6
- SQLite
- SQLAlchemy 2
- Pydantic 2
- openpyxl
- python-docx + docxtpl
- `holidays` — только как источник базового календаря праздников; ручные исключения имеют приоритет
- platformdirs
- pytest + pytest-qt
- uv
- PyInstaller для сборки

Не добавлять web-server, React, Electron, FastAPI, PostgreSQL, Docker или pandas без отдельного обоснования и согласования.

## 3. Архитектурные ограничения

- UI не содержит бизнес-логики.
- XLSX-парсер не знает о UI.
- DOCX-экспортер не знает о UI.
- Все бизнес-правила покрываются unit-тестами.
- Все пути к файлам — через `pathlib` и `platformdirs`.
- Никаких Windows-only путей/COM/Office automation.
- Word/Excel не должны быть обязательны для работы приложения.
- Часы и ставки хранить через `Decimal`, не `float`.
- Не использовать имя файла как источник истины: преподаватель, ставка и тип занятости читаются из содержимого XLSX.
- Импорт должен быть идемпотентным: считать SHA-256 файла и предупреждать о повторном импорте.
- Не молча угадывать изменившийся формат XLSX. При несовместимой структуре — понятная ошибка `Формат файла не распознан`.

## 4. Ключевые бизнес-правила

- 1 ставка = 900 часов.
- Эффективная ставка для расчета задается на уровне преподавателя и подтверждается пользователем; не суммировать ставки из нескольких импортированных файлов автоматически.
- Для целей программы плановые часы импортированных индивидуальных планов считаются «фактическими» для распределения.
- Источники нагрузки можно включать/исключать из расчета фактической нагрузки вручную.
- Группы, начинающиеся с `ИДПО_`, относятся к ИДПО; их часы вычитаются из расчетной нагрузки, потому что оплачиваются отдельно.
- В почасовку допустимы только аудиторные виды: лекции, практические, лабораторные.
- Максимальная почасовка — 300 часов на сотрудника.
- Конкретные дисциплины/группы пользователь выбирает вручную; программа не выбирает семестр за пользователя.
- 1 семестр: сентябрь–декабрь.
- 2 семестр: январь опционально, затем февраль–май.
- Помесячное значение по дисциплине-группе: 0 или положительное число, кратное 2.
- Одно занятие в печатной форме = 2 часа.
- Занятия генерируются только Пн–Пт, с учетом праздников, исключенных дат и пожеланий преподавателя.
- В одну дату у одного преподавателя один и тот же временной слот нельзя использовать дважды. Промежутки между занятиями допустимы.
- Временные слоты перечислены в `docs/08_SCHEDULER_SPEC.md` и должны храниться в конфигурации/БД, а не быть размазаны по коду.

## 5. Неопределенности, которые нельзя «додумывать»

См. `docs/10_OPEN_QUESTIONS.md`. Если реализация упирается в один из этих пунктов, сделать настройку/явное подтверждение пользователя или запросить решение. Не зашивать предположение как факт.

## 6. Порядок разработки

1. Domain-модели и бизнес-правила.
2. Парсер XLSX + тесты на приватных fixture-файлах.
3. Нормализация нагрузки и anomaly detection.
4. SQLite persistence.
5. Расчет почасовки.
6. Ручной конструктор помесячного плана.
7. Генератор дат/времени.
8. DOCX exporter.
9. PySide6 UI.
10. Сборки Windows/macOS.

## 7. Definition of Done для любой задачи

- есть тесты на бизнес-логику;
- код проходит `ruff`;
- тесты проходят на текущей ОС;
- нет OS-specific путей;
- ошибка показывается пользователю понятным текстом;
- не изменены бизнес-правила без обновления документации;
- для изменения схемы БД предусмотрена миграция или безопасный upgrade path.
